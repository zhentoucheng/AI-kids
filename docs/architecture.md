# 架构与数据流

## 分层

```
物理层   门锁(指纹/密码)   客厅摄像头     智能音箱      室外摄像头
              │                │            ▲   │
              ▼                ▼            │   ▼
转换层     米家云         go2rtc :1984 ─────┘  xiaomusic :58090
              │                │                    (歌单引擎)
              ▼                ▼
中枢层   Home Assistant   Frigate :8971    mosquitto :1883
         (实体状态)        (人数/事件)       (MQTT 总线)
              │                │                  │
              ▼                ▼                  ▼
应用层   ① 回家播英语      ② 小考官           ③ 管家小克
         (HA 自动化)       (kaoguan)          (keke)
```

所有容器跑在同一台 NAS 上，靠 MQTT 和 HA 的 REST API 通信。没有数据库，没有消息队列的复杂玩法。

## 三条链路

| 链路 | 触发源 | 判定 | 出口 |
|---|---|---|---|
| **A 回家播英语** | 门锁指纹（米家云识人） | 当天姐姐到家后，妹妹进门不再播 | 音箱歌单 |
| **B 客厅随机抽考** | Frigate 人数 ≥1 且持续 40s | 三道闸：时段 / 间隔 / 额度 | 音箱 TTS |
| **C 管家主动开口** | 定时器 / 门锁事件 / 打闹判定 | 五个事件各自的条件 | 音箱 TTS |

链路 A 走 HA 自动化，不经过两个 Python 容器。B 和 C 各是一个常驻进程。

## 抢麦仲裁

音箱只有一个，三个服务都想说话。规则：

| 说话者 | 什么时候闭嘴 |
|---|---|
| 小考官 | 门外任何开锁 → 静默 15 分钟（让"英语 → 问候 → 孩子回话"走完） |
| 管家 | 读 MQTT `kaoguan/state` 的 `asking`，考官在出题/报答案时闭嘴 |
| 回家播英语 | 自带头白 25 秒，播完才轮到别人 |

小考官**故意不把**"音箱正在播放"当阻塞条件——它整天在放故事，那样会永远出不了题。

## 数据流：一次抽考的完整链路

```
Frigate  /api/stats          人数 = 1，持续 42s
   │
   ├─→ 三道闸：现在 15:30? 距上次 35min? 今天第 4 次?
   │
   ├─→ 判断谁在家：Frigate 人脸 ∪ 门锁最近开锁名单
   │
   ├─→ 加权随机点名 → "姐姐"
   │
   ├─→ 出题
   │     ├─ 90%  抓帧 + 六年级词表(130词) → 视觉模型
   │     │        返回 {scene:"在写作业", word:"pencil", zh:"铅笔"}
   │     └─ 10%  词表随机抽
   │
   ├─→ 拼题面 → HA text.set_value → 音箱
   │
   ├─→ 估算念完要多久（4.5 字/秒）+ 15s
   │
   └─→ 报答案（英文答案额外念拼写）
```

## 状态存放

没有数据库。全部是文件：

| 文件 | 内容 | 生命周期 |
|---|---|---|
| `state.json` | 今日出题次数、最后出题时间 | 每天重置 |
| `sentence_cache.json` | 单词例句缓存（同一个词只调一次模型） | 永久 |
| `memory/YYYY-MM-DD.jsonl` | 管家收到的孩子回执 | 保留 30 天 |

## 为什么不用消息队列 / 数据库

因为这是家庭场景，一台跑了好几年的老 NAS：

- 消息量：一天几百条，MQTT 足够
- 状态量：几个 JSON 文件，坏了删掉重来
- 排查：`docker logs` 一眼能看完

引入 Redis / Postgres 只会让"NAS 挂了怎么恢复"变成一道难题。
