# 踩坑详解

README 里是摘要，这里是完整的现场记录。每条都带实测数据。

---

## 一、视觉判定不可信

### 现象

同一个静止画面、同一个模型、同一个提示词，连问 15 次"画面里两个孩子在干什么"：

| 判定 | 次数 |
|---|---|
| 打闹 | 8 |
| 安静 | 2 |
| 空 | 4 |

三分之一的概率连"有没有人"都判错。

### 根因

单帧是一张图，模型没有任何时序信息。孩子举手够个东西，和推搡一下，在一帧里长得一样。

### 改法

1. **三帧联合**：一次请求带 3 帧，间隔 1.5 秒，让模型看趋势
2. **`min_people=2` 硬防线**：Frigate 的人数统计比模型可靠，人不够直接不判
3. **连续 2 次确认**：两次独立判定都是"打闹"才开口

改完误报率从肉眼可见降到可以接受。

## 二、门锁状态必须查历史

### 现象

回家问候经常不触发，明明孩子进门了。

### 根因

真实事件序列：

```
16:07:03  outside_unlock   ← 门外开锁
16:07:25  lock_inside      ← 门内上锁（20 秒后自动）
```

轮询间隔 2 秒，等拿到数据时状态早变成 `lock_inside` 了。**读当前值必然漏掉每一次进门。**

### 改法

`/api/history/period?start=...&end=...` 在时间窗内找**事件点**，不是找**状态**。

判据：任何"当前状态"都可能是过期的，只有事件流是真实的。

## 三、三源探测门锁信号

### 现象

`lock_action` 和 `lock_key_id` 是云轮询，不实时。实测 16:07 孩子指纹开门，实体停在 09:46 不动。

### 更坑的

米家消息实体 `sensor.xxx_message` 是实时源，但它是**单值实体**——消息互相覆盖。"门外开锁"被紧随的"门已上锁"顶掉，**概率性丢包**。

### 改法

两路并行 + `lock_key_id` 的设备侧 `timestamp` 跳变兜底。三源探测，任一路命中就算。

## 四、唤醒词同音容错

### 现象

喊"小克"，云转写回来是"小客""小柯""小哥""小科"。

### 为什么不能精确匹配

因为转写不是你能控制的。同一个发音，不同时间转写结果不同。

### 改法

```
匹配规则：以「小」开头 + 第二个字在同音字表里
同音字表：克 客 柯 科 可 刻 课 嗑 恪 溘 哥
```

但这会产生假阳性：小哥哥、小可爱、小柯基。

所以叠一层**假阳性词表**，规则是：必须"小"+同音字组成**整词**才算否决。比如"小柯基"整词命中 → 否决；"小柯今天..."不是整词 → 放行。

## 五、定时事件要排在视觉检查之前

### 现象

睡前问候（20:45）永远不触发。

### 根因

打闹检查的时段是 16:00–21:00，每 150 秒跑一次。它先执行，而且它的时段**盖住了** 20:45。等轮到睡前问候，条件已经被前面的分支吃掉了。

### 改法

定时事件（到点就要说）必须排在"要不要看一眼"型检查（打闹、有人进门）之前。

这是个通用原则：**确定性事件优先于概率性事件**。

## 六、群晖 `db` 日志驱动假死

### 现象

容器 `docker ps` 显示 `Up 5 days`，但服务完全没响应。

### 根因

群晖默认日志驱动是 `db`，SQLite 写满或者管道阻塞后，容器进程还活着但写日志的调用会阻塞，整个进程僵住。

### 改法

所有常驻容器改 `json-file` + 轮转：

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

这条和本项目无关，但只要你在群晖上跑常驻容器，就该改。

## 七、小米云 device_id 的两个坑

### 坑 1：serviceToken 的取法

token 结构是 `{passToken, userId, deviceId, micoapi: [deviceId(24), serviceToken(216)]}`。

必须取 `micoapi[1]`。`micoapi[0]` 是设备 ID，拿它当 token 必然 401。

### 坑 2：查对话记录要用音箱的 deviceId

接口按 deviceId 过滤，这个 ID 必须是**音箱**的 UUID（来自 xiaomusic 的 `setting.json: devices[did].device_id`）。

token 里那个 `deviceId` 字段（16 字符）是**登录设备**的 ID。传它进去 → 接口返回 `code=0`，但 `records` 恒为空。

看起来像"孩子今天没说过话"，其实查错了设备。实测：音箱 UUID 立刻拿到历史，token 里的返回 0 条。

## 八、配额别设太小

### 现象

设 `max_per_day: 6`，中午 12:46 就烧完了，下午一道题都没有。

### 改法

30 次。因为触发条件本身已经足够保守（有人 + 坐够 40 秒 + 最小间隔 30 分钟），日额度不是主要限制。

---

## 九、报答案的时机

### 现象

题还没念完就报答案。

### 根因

固定延迟 15 秒不够。长题目念完就要 20 秒。

### 改法

报答案时间 = **念题估算时长**（字数 / 4.5 字每秒）+ 15 秒。

4.5 字/秒是实测的中文 TTS 语速，小爱、天猫、小度都在这个量级附近。

---

## 十、并行不阻塞，只错开

门锁"回家播英语"和考官出题是两条独立链路，互不阻塞。

唯一要错开的是**谁在说话**：门外一开锁，考官静默 15 分钟，让"英语播完 → 管家问候 → 孩子回话"走完，再轮到出题。

不要做"音箱正在播放就阻塞"这种判断——音箱整天在放故事，那样永远出不了题。
